## F1 · P2 · 部分缓解，尚未关闭：300 秒阶段预算不等于 600 秒任务 deadline

**主要位置：`packages/backend/src/events/group.ts:99–115`。**

新增 `JEV_STAGE_BUDGET_MS = 300_000` 确实避免了旧版 Jev 循环无阶段上限的问题；但 `endsAt` 在 Jev 阶段开始时才计算，结束后也没有继续约束原归组、复核和写入。因此不能保证注释所说的“过期任务不再请求或写入”。

证据链：

- `group.ts:366–368`：召回先于 Jev 阶段预算开始。
- `group.ts:378–380`：Jev 完成后继续执行原 `judgeBatch()`。
- `group.ts:435–450`：低余弦候选可逐个执行 `confirmMerge()`，并非最多复核一次；前一个复核拒绝后可继续下一个。
- `providers/llm.ts:172`：batch 和 review 的 HTTP 默认各有独立的 120 秒超时，没有共享剩余任务时间。
- `jobs/queue.ts:49`：整个 group job 的过期时间仍是 600 秒。
- `jobs/queue.ts:165–167`：包装器只把 `job.data` 传给业务函数，没有传递 `job.signal`；业务事务也没有任务过期检查。

### 一个满足所有局部限制的反例

假设有 7 个候选，Jev 均不否决，其中至少 3 个被原 batch 判断为 `SAME_OCCURRENCE` 且余弦小于 0.85；前两次复核返回 `UNRELATED`，第三次确认同一事实。

| 阶段 | 用时（秒） | 累计（秒） |
|---|---:|---:|
| 7 次 Jev，每次 40 秒 | 280 | 280 |
| 原 batch | 110 | 390 |
| 第一次复核 | 110 | 500 |
| 第二次复核 | 110 | 610 |
| 第三次复核 | 110 | 720 |

Jev 阶段小于 300 秒，单个请求都小于 120 秒；但队列在第 600 秒已经超时。当前控制流仍可在第 610 秒发起第三次付费复核，随后进入写入逻辑。这里甚至没有计入召回和数据库开销。

**验证边界：** 使用当前安装的 pg-boss `resolveWithinSeconds()` 与 `TestClock`，按上述阶段顺序模拟延迟，断言队列 600 秒超时、第三次复核阶段 610 秒启动时 signal 已 aborted、720 秒仍到达模拟写入入口。不是实际 `groupArticle()` 全链路测试，也不是线上延迟观测；没有实际请求或事件写入。真实代码的可达分支由以上位置确认。

### 修复建议与验收条件

- 为整个归组执行建立共享 deadline / 取消信号，贯穿召回、Jev、原 batch、复核以及提交前检查；不要仅再缩小一个阶段的固定预算，或只增大队列过期时间。
- 请求开始前检查任务是否有效，正在进行的 HTTP 应接收取消信号；失效后不得购买下一次请求或提交本次归组结果。已经收到的付费响应按现有回执机制保留以供恢复。
- 增加队列级回归：Jev 本身未超时，但后续多候选复核使整个任务到期；断言后续请求和业务提交均被阻止，并检查回执恢复行为。
- Spec S4 已补充 300 秒阶段预算，但其“为后续留出余量”仍不是端到端上限保证，需同步明确任务生命周期约束。

这是第一轮 F1 的剩余部分，不是声称所有正常请求都会超过 600 秒。风险是慢响应组合下，过期 handler 继续付费和写入，并可能与后续执行交错。
